# Invoice Quote Filler v0.2.1 Template Capacity Plan

## 1. Назначение v0.2.1

Цель v0.2.1 - перейти от временного safety guard на 5 позиций к безопасной
поддержке реальных КП на 30-50+ позиций на блок.

Этап называется `template capacity / extended rows`, потому что основной риск
сейчас связан не с JSON-контрактом, а с физической ёмкостью Excel-шаблона и
безопасностью строк, формул, итогов, примечаний, подписей и layout.

v0.2.1 не должен превращать временный лимит 5 позиций в бизнес-ограничение.
Вместо этого он должен явно проверять capacity шаблона и останавливаться без
создания output, если количество позиций больше проверенной ёмкости.

## 2. Почему Текущий Лимит 5 Существует

Старый MVP `scripts/fill_invoice_quote_draft.py` рассчитан на маленький
проверенный диапазон:

- `MAX_ITEMS = 5`;
- `ITEM_START_ROW = 17`;
- `ITEM_END_ROW = 21`;
- итог находится в `I22`;
- подписи находятся ниже табличной части;
- `validate_contract()` останавливает `items > 5`;
- `fill_allowed_cells()` пишет позиции только в строки `17-21`;
- `verify_output()` проверяет формулы, merged ranges, подписи, шапку и
  drawing/media chain.

Текущий лимит нужен, чтобы не затереть итог, примечания, подписи, формулы,
merged cells, layout и служебные части Excel-файла.

## 3. Почему Нельзя Просто Заменить 5 На 50

Простая замена числа `5` на `50` небезопасна.

Есть двойной программный лимит:

- старый MVP останавливает `items > 5` через `MAX_ITEMS`;
- v0.2 separate layer останавливает блоки `> 5` через `MAX_ITEMS_PER_BLOCK`.

Есть также физический лимит текущего шаблона:

- строки позиций находятся в `17-21`;
- итог уже стоит в `I22`;
- ниже находятся примечания и подписи.

Если разрешить 30-50+ позиций без расширенного шаблона, генератор начнёт писать
поверх итога, примечаний, подписей или layout. Поэтому сначала нужна проверенная
template capacity, а уже потом изменение кода.

## 4. Рекомендуемый Путь: Расширенный Шаблон

Рекомендуемый путь для v0.2.1 - отдельный заранее подготовленный Excel-шаблон
на 30-50+ строк.

В таком шаблоне должны быть заранее настроены:

- строки позиций;
- формулы по строкам;
- итоговая формула;
- примечания;
- подписи;
- шапка и реквизиты;
- merged ranges;
- layout и, если применимо, область печати;
- drawings/media.

Capacity должна быть либо определяемой из шаблона, либо явно заданной в запуске
или конфигурации. Если `items > capacity`, скрипт должен останавливаться до
создания output.

## 5. Нерекомендуемый Пока Путь: Динамическая Вставка Строк

Динамическая вставка строк потенциально удобнее, но для первого v0.2.1 шага она
слишком рискованна.

Основные риски:

- повреждение формул;
- сдвиг или потеря merged ranges;
- повреждение подписей;
- затирание примечаний;
- повреждение drawings/media;
- потеря или неверное расширение области печати;
- непредсказуемое копирование стилей и высот строк.

Динамическую вставку строк стоит рассматривать как отдельный spike после
проверенного пути с расширенным шаблоном.

## 6. Возможная Архитектура v0.2.1

### A. Не Менять Старый MVP

Сделать capacity-aware fill/verify в v0.2 layer.

Плюсы:

- старый проверенный MVP остаётся стабильным;
- изменения локализованы в v0.2 контуре;
- проще удержать границы риска.

Минусы:

- часть логики заполнения может дублироваться;
- нужно аккуратно переиспользовать helper-функции старого MVP без изменения его
  публичного поведения.

### B. Параметризовать Старый MVP

Аккуратно параметризовать `scripts/fill_invoice_quote_draft.py` после отдельного
решения Игоря.

Плюсы:

- меньше дублирования логики;
- один общий filler может работать с разной capacity.

Минусы:

- выше риск регрессии старого MVP;
- потребуется более широкий набор тестов;
- изменение старого MVP нельзя делать без отдельного подтверждения.

### C. Отдельный Расширенный Filler Для v0.2.1

Создать отдельный расширенный filler для template capacity.

Плюсы:

- чёткая изоляция нового поведения;
- проще тестировать v0.2.1 как отдельный контур.

Минусы:

- появляется ещё один скрипт;
- потребуется следить за расхождением контрактов и helper-логики.

## 7. Предпочтительная Архитектура Для Первого Шага

Для первого v0.2.1 шага предпочтительно:

- старый MVP не трогать;
- сделать отдельный capacity-aware слой в v0.2.1;
- использовать generated test template на 30-50 строк в тестах, без добавления
  Excel-файлов в Git;
- держать реальный расширенный Excel-шаблон вне Git до отдельного решения;
- проверять `items <= capacity` до создания output;
- если `items > capacity`, останавливаться без output.

Это сохраняет старый рабочий контур и даёт безопасный путь к реальным КП.

## 8. Какие Файлы В Будущем Менять

Вероятно:

- `scripts/fill_invoice_quote_v0_2_separate.py`;
- `tests/test_fill_invoice_quote_v0_2_separate.py`.

Возможно после отдельного решения:

- `scripts/fill_invoice_quote_draft.py`.

По умолчанию старый MVP не менять.

## 9. Какие Файлы Не Трогать Без Отдельного Решения

Без отдельного решения не трогать:

- реальные Excel-шаблоны;
- PDF;
- validator;
- examples;
- `AGENTS.md`;
- `requirements.txt`.

Excel-шаблоны не добавлять в Git без отдельного подтверждения.

## 10. Тесты Для v0.2.1

Нужные тесты:

- generated test template на 30-50 строк без Excel-файла в Git;
- capacity detection или explicit capacity;
- `items == capacity` создаёт output;
- `items > capacity` останавливается без output;
- existing output не перезаписывается;
- partial output не остаётся;
- формулы итогов нового диапазона сохраняются;
- подписи, примечания, merged ranges, drawings/media сохраняются;
- старый MVP не меняется, если выбран путь без его изменения.

Тестовый расширенный шаблон должен создаваться кодом в `tmp_path`, а не храниться
как `.xlsx` в репозитории.

## 11. Human Approval Points

Игорь отдельно подтверждает:

- создание или использование расширенного Excel-шаблона;
- выбранную capacity;
- переход от 5 к 30-50+ позициям;
- любые изменения старого MVP;
- ручную приёмку output.

## 12. Следующий Рекомендуемый Шаг

Следующий шаг - не код.

Сначала нужно:

1. Подготовить или скопировать расширенный шаблон вне Git.
2. Проверить его инспектором.
3. Зафиксировать фактическую capacity шаблона.
4. Только после этого переходить к v0.2.1 code step.

До этого динамическую вставку строк не делать основным путём.
