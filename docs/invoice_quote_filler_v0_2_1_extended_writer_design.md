# Invoice Quote Filler v0.2.1 Extended Writer Design

## 1. Зачем Нужен Extended Writer

Старый MVP `scripts/fill_invoice_quote_draft.py` рассчитан на маленький
проверенный Excel-шаблон с 5 строками позиций. Его safety-модель привязана к
фиксированному диапазону строк, формулам, итогам, подписям, шапке, реквизитам и
drawing/media chain текущего шаблона.

Опция `--template-capacity` теперь задаёт явный preflight capacity source и по
умолчанию равна `5`. Это позволяет заранее остановить генерацию, если входных
позиций больше проверенной ёмкости шаблона. Но сама по себе эта опция не даёт
генерацию на 30-50+ строк и не меняет физический layout Excel-файла.

Для реальных КП нужен отдельный `extended writer`, который сможет безопасно
писать позиции в заранее подготовленный расширенный Excel-шаблон. Такой writer
должен работать только с известной layout/capacity моделью и не должен обходить
ограничения старого MVP автоматически.

## 2. Что Extended Writer Должен Делать

Будущий `extended writer` должен принимать:

- flat payload с позициями КП;
- template layout/capacity;
- путь к заранее подготовленному расширенному шаблону;
- путь к output вне Git.

Основная логика:

- проверить входной flat payload до открытия output;
- проверить, что количество позиций не превышает template capacity;
- писать позиции только в разрешённый диапазон строк расширенного шаблона;
- сохранять формулы строк и итогов;
- не трогать итоги, примечания, подписи, шапку, реквизиты и служебные области;
- не трогать drawing/media chain;
- проверять formulas, merged ranges, signatures, headers и media chain до и
  после сохранения;
- создавать output только вне Git;
- не перезаписывать существующий output;
- при ошибке чистить temp-файлы и не оставлять partial output.

Writer должен быть fail-closed: если layout, capacity, formulas, merged ranges,
signatures, headers или media chain не подтверждены, генерация должна
останавливаться до появления готового output.

## 3. Что Extended Writer Не Должен Делать

`extended writer` не должен:

- менять цену, срок, комплектацию или `project_spec`;
- подтверждать коммерческое предложение;
- отправлять КП клиенту;
- делать динамическую вставку строк на первом этапе;
- использовать реальный `.xlsx` из Git как рабочий шаблон;
- менять старый MVP `scripts/fill_invoice_quote_draft.py` без отдельного
  решения;
- автоматически считать `--template-capacity > 5` разрешением писать 30-50+
  строк старым writer;
- исправлять или нормализовать проектные данные без отдельного контура
  reconciliation/check.

Writer остаётся техническим контуром подготовки черновика. Он не является
источником бизнес-подтверждения цены, сроков, комплектации, границы поставки или
готовности КП к отправке.

## 4. Возможная Архитектура

Предпочтительный первый вариант - отдельный модуль или скрипт, например
`scripts/fill_invoice_quote_extended.py`. Это позволит изолировать новое
поведение от старого MVP и не расширять blast radius v0.2.1.

Возможные компоненты:

- `fill_invoice_quote_extended.py` как явная entry point для расширенного
  шаблона;
- shared helper для snapshot/verify, если часть логики старого MVP можно
  безопасно переиспользовать без изменения его публичного поведения;
- отдельная модель layout/config для Excel-шаблона;
- отдельный verify-контур для сравнения workbook state до и после записи.

Минимальная layout/config модель может включать:

- `item_start_row`;
- `item_end_row`;
- `capacity`;
- `total_row`;
- `signature_range`;
- `header_ranges`;
- `requisites_ranges`;
- `formula_cells`;
- `merged_ranges`;
- `media_chain_expected`;
- `protected_ranges`;
- `output_directory_policy`.

В будущем эта модель может быть связана с manifest, но manifest не должен
реализовываться в текущем design-only шаге. На первом code step layout/config
может быть тестовой структурой, созданной внутри теста, чтобы не добавлять
реальный `.xlsx` и не принимать преждевременное решение о формате manifest.

## 5. Подключение К v0.2 Separate Layer

Старый MVP должен остаться default writer для capacity `5`. Это сохраняет
обратную совместимость и защищает проверенный сценарий на 5 строк.

Для будущего подключения к v0.2 separate layer возможен явный режим writer:

```text
--writer mvp|extended
```

Рекомендуемые правила:

- `--writer mvp` использует старый MVP и допускает только проверенную capacity
  `5`;
- `--writer extended` использует новый extended writer и требует layout/capacity
  расширенного шаблона;
- extended writer включается только при явном выборе;
- `--template-capacity > 5` не должен автоматически обходить старый MVP без
  явного writer mode;
- если writer mode не указан, v0.2 separate layer должен сохранять текущее
  безопасное поведение.

Такой подход разделяет два решения: preflight capacity и фактический writer.
Capacity говорит, сколько строк проверено в шаблоне; writer mode говорит, какой
код имеет право писать в этот шаблон.

## 6. Тестовая Стратегия

Будущие тесты должны использовать тестовый расширенный Excel-шаблон, созданный
кодом в `tmp_path`. `.xlsx` fixture не нужно хранить в Git.

Нужные проверки:

- тестовый расширенный шаблон создаётся кодом в `tmp_path`;
- генерация 6+ позиций проходит только через extended writer;
- output не создаётся при превышении capacity;
- existing output не перезаписывается;
- partial/temp output чистится при ошибке;
- формулы итогов сохраняются;
- формулы строк позиций сохраняются или восстанавливаются по заданной модели;
- подписи сохраняются;
- шапка и реквизиты сохраняются;
- merged ranges сохраняются;
- drawing/media chain сохраняется;
- старый MVP остаётся неизменным по SHA256;
- старые сценарии на 5 строк не ломаются;
- `--template-capacity > 5` без explicit extended writer не приводит к записи
  старым MVP за пределами его проверенного диапазона.

Отдельно стоит тестировать fail-closed поведение:

- неизвестная capacity останавливает генерацию;
- конфликт layout/config останавливает генерацию;
- отсутствующая формула итога останавливает генерацию;
- изменённая signature/header/media snapshot останавливает генерацию;
- output path внутри Git останавливает генерацию.

## 7. Human Approval Points

Отдельное подтверждение Игоря требуется на:

- изменение реального Excel-шаблона;
- выбор реального extended template;
- фактическую capacity реального шаблона;
- добавление `.xlsx` в Git;
- переход к manifest;
- переход к динамической вставке строк;
- изменение старого MVP;
- использование generated output как клиентского КП.

Без этих подтверждений extended writer должен оставаться техническим черновым
контуром и не должен менять реальные Excel-файлы или производственные правила.

## 8. Рекомендуемый Следующий Шаг После Design

Следующий безопасный шаг - сначала зафиксировать acceptance criteria для
extended writer.

После согласования acceptance criteria можно сделать минимальный code step:

1. создать тестовый расширенный шаблон кодом в `tmp_path`;
2. добавить проверку записи 6+ позиций только через explicit extended writer;
3. проверить, что формулы, подписи, шапка, merged ranges и media chain
   сохраняются;
4. проверить, что output не создаётся при превышении capacity.

Только после этого стоит думать о manifest или диагностике
`inspect_excel_template.py`. Динамическая вставка строк должна оставаться
отдельным будущим spike, а не частью первого extended writer шага.
