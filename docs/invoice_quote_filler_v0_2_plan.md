# План v0.2 заполнителя счёта-КП

## 1. Цель v0.2

Версия v0.2 должна заложить поддержку проектов, где позиции КП разделены
по блокам проекта. Для этого входной JSON должен перейти от плоского `items`
к структуре `project_blocks`.

Вторая цель v0.2 - ввести явный режим генерации `output_mode`, чтобы один и
тот же проверенный набор проектных данных можно было использовать для разных
вариантов output:

- один общий КП с секциями по блокам;
- отдельные КП по каждому блоку;
- оба варианта сразу.

v0.2 остаётся инструментом подготовки черновика. Она не утверждает финальные
цены, сроки, комплектацию, корректность OCR или готовность КП к отправке
клиенту.

## 2. Исходные наблюдения по КП №268

Реальный КП №268 по ТОО «Kreativ-SP» показал рабочую структуру для будущей
v0.2:

- оба блока находятся в одном листе КП;
- `C16 = Пятно 8`;
- `C39 = Пятно 9`;
- `Пятно 8` содержит примерно 21 позицию;
- `Пятно 9` содержит примерно 22 позиции;
- внутри блоков есть подзаголовок `Коммерческие помещения`;
- промежуточных итогов по блокам нет;
- общий итог находится в `I63 = SUM(I17:I62)`;
- проектные PDF без текстового слоя, поэтому автоматическое чтение проекта не
  подтверждено.

В КП основными названиями секций должны быть `Пятно 8` и `Пятно 9`.
Названия `Орынбор 8 Блок` и `Орынбор 9 Блок` следует хранить как
source/project reference, но не использовать как основное название секции в КП.

## 3. Основной принцип

Один JSON v0.2 должен содержать единый массив `project_blocks`. Этот массив не
должен зависеть от того, какой output нужен в конкретном запуске.

Поле `output_mode` определяет только способ генерации:

- `single_workbook_sections` - общий КП с секциями по блокам;
- `separate_workbooks_by_block` - отдельный output-файл по каждому блоку;
- `both` - общий КП и отдельные КП по блокам.

Таким образом, `project_blocks` является источником данных, а `output_mode` -
политикой вывода.

## 5. Поля блоков и секций

`block_name` - стабильный технический идентификатор блока. Он нужен для
валидации, имён output-файлов и связи с отчётами.

`block_label_for_quote` - человекочитаемое название секции в КП. Для кейса
Орынбор это `Пятно 8` и `Пятно 9`.

`project_code` - проектный шифр или ссылка на проект. Если он не подтверждён,
значение должно оставаться `нужно уточнить`.

`source_file` - исходный проектный файл или спецификация, из которой получены
данные блока.

`source_pages` - список диапазонов страниц. Формат диапазона:

```json
{
  "from": 32,
  "to": 37,
  "note": "спецификация"
}
```

`subsections` - обязательный уровень структуры внутри блока. Он нужен для
подзаголовков вроде `Коммерческие помещения`. Если позиции идут сразу под
блоком без отдельного подзаголовка, `subsection_name` может быть `null`.

## 6. Output mode

### single_workbook_sections

Режим по умолчанию для v0.2.

Генератор создаёт один общий КП. В табличной части последовательно выводятся
секции по `project_blocks`:

1. строка/метка блока `block_label_for_quote`;
2. основной subsection без названия, если он есть;
3. именованные subsections, например `Коммерческие помещения`;
4. следующий блок;
5. общий итог.

Промежуточные итоги по каждому блоку в первый v0.2 не включаются без отдельного
решения Игоря.

### separate_workbooks_by_block

Генератор создаёт отдельный output-файл для каждого элемента
`project_blocks[]`.

В каждом output используется тот же `document`, `customer`, `project` и
`commercial_terms`, но табличная часть содержит только один блок.

Этот режим безопасен как первый технический шаг, потому что уменьшает число
строк в одном workbook и снижает риск повредить формулы, подписи, сетку,
логотип или drawing parts.

### both

Генератор формирует:

- один общий КП в режиме `single_workbook_sections`;
- отдельные КП по каждому блоку в режиме `separate_workbooks_by_block`.

Данные не должны дублироваться в JSON. Все output-файлы должны строиться из
одного и того же проверенного массива `project_blocks`.

## 7. OCR/source extraction контур

Проектные PDF без текстового слоя нельзя считать надёжным источником для
автоматического КП. Если PDF распознан через OCR или сохранён как searchable
PDF, данные всё равно считаются черновыми.

Правильный контур:

```text
PDF/OCR -> project_spec.json -> ручная проверка -> генерация черновика КП -> сверка
```

Требования:

- результат OCR или парсинга PDF должен попадать в отдельный `project_spec.json`;
- `project_spec.json` должен пройти ручную проверку Игоря или инженера;
- `source_data_manually_verified = true` может ставить только Игорь или инженер
  после ручной проверки;
- генератор КП не должен сам утверждать, что проект прочитан корректно;
- OCR confidence и комментарии не должны попадать в основное КП как
  утверждённые данные;
- OCR confidence и комментарии можно хранить в `metadata` или отдельном
  `extraction_report`.

PDF/OCR не должен идти напрямую в финальное КП.

## 8. Контуры источников данных

### Вручную подготовленный JSON

Самый безопасный источник для первого v0.2.

Плюсы:

- проще валидировать;
- легко требовать ручное подтверждение;
- ниже риск перепутать блоки или количества;
- можно начать с validation tests без Excel-генерации.

Минусы:

- данные вводятся вручную;
- возможны ручные ошибки.

### Excel/текстовая спецификация

Промежуточный по риску контур.

Плюсы:

- обычно лучше структурирован, чем OCR-PDF;
- проще извлекать таблицы и позиции;
- можно сохранять ссылки на строки/листы источника.

Минусы:

- формат спецификаций может отличаться от проекта к проекту;
- есть риск принять служебные строки за позиции;
- всё равно нужна ручная проверка.

### OCR-PDF

Самый рискованный контур.

Плюсы:

- позволяет работать с исходными проектными PDF;
- потенциально уменьшает ручной ввод.

Минусы:

- PDF без текстового слоя не является надёжным источником;
- OCR может ошибаться в названиях, количествах, единицах и шифрах;
- таблицы могут быть распознаны с потерей строк или колонок;
- требуется отдельный отчёт извлечения и ручная сверка.

Безопасный OCR spike:

1. взять 2-3 страницы спецификации;
2. извлечь таблицу;
3. сформировать черновой `project_spec.json`;
4. вручную сверить результат;
5. только после этого расширять подход на весь проект.

## 9. Reconciliation/check контур

Нужен отдельный будущий режим сверки:

```text
project_spec.json + готовый КП -> отчёт расхождений
```

Режим сверки должен проверять:

- наличие всех блоков;
- названия блоков;
- наличие подзаголовков;
- позиции внутри каждого subsection;
- количества;
- единицы измерения;
- позиции из JSON, которые не попали в КП;
- позиции в КП, которых нет в JSON;
- итоговые суммы, если цены подтверждены;
- общий итог и будущие промежуточные итоги, если они будут включены.

Отчёт расхождений не должен автоматически исправлять КП. Он должен показывать,
что требует ручной проверки.

## 10. Безопасный порядок разработки

Этап 1: документ v0.2 plan.

Этап 2: подготовить example JSON v0.2 без изменения Excel.

Этап 3: добавить validation tests без Excel-генерации. На этом этапе нужно
проверять структуру `project_blocks`, `output_mode`, `subsections`,
`source_pages` и safety flags.

Этап 4: реализовать генерацию `separate_workbooks_by_block` или
`single_workbook_sections` только после отдельного решения Игоря о первом
режиме реализации.

Этап 5: OCR spike отдельно от генератора КП.

Динамическую вставку строк в Excel нельзя считать безопасной частью первого
v0.2 без отдельного spike и проверок roundtrip.

## 11. Риски

- OCR-ошибки в названиях, количествах, единицах и шифрах;
- перепутанные блоки;
- потеря подзаголовков вроде `Коммерческие помещения`;
- динамическая вставка строк;
- повреждение формул итогов;
- повреждение логотипа, drawings, media parts или printer settings;
- восприятие черновика как финального КП;
- цены без подтверждения Игоря;
- сроки без подтверждения Игоря;
- добавление Excel-файлов в Git по ошибке.
