# Handoff v0.2 заполнителя счёта-КП

## 1. Текущий статус v0.2

На момент handoff по v0.2 завершены и зафиксированы:

- архитектурный план:
  `docs/invoice_quote_filler_v0_2_plan.md`;
- пример входного JSON v0.2:
  `examples/invoice_quote_draft_v0_2_blocks.example.json`;
- validation-layer:
  `scripts/validate_invoice_quote_v0_2.py`;
- тесты validator:
  `tests/test_validate_invoice_quote_v0_2.py`;
- CI на GitHub Actions зелёный;
- ветка `main` синхронизирована с `origin/main`.

Excel-генерация v0.2 ещё не начиналась. Текущий MVP-заполнитель
`scripts/fill_invoice_quote_draft.py` не менять без отдельного решения.

## 2. Уже принятая архитектура

Для v0.2 принят принцип: один набор `project_blocks` используется для разных
режимов output. Способ вывода задаёт поле `output_mode`, а не отдельная
структура данных.

Допустимые значения `output_mode`:

- `single_workbook_sections`;
- `separate_workbooks_by_block`;
- `both`.

`subsections` являются обязательным уровнем структуры внутри блока. Они нужны,
чтобы не потерять подзаголовки вроде `Коммерческие помещения`.

Для кейса Орынбор принято:

- `Пятно 8` и `Пятно 9` - названия секций в КП;
- `Орынбор 8 Блок` и `Орынбор 9 Блок` - source/project reference, но не
  основное название секции в КП.

PDF/OCR не должен идти напрямую в финальное КП. Правильный контур:

```text
PDF/OCR -> project_spec.json -> ручная проверка -> генерация черновика КП -> сверка
```

Генератор КП не должен сам утверждать, что проект прочитан корректно.

## 3. Что уже проверяет validator

`scripts/validate_invoice_quote_v0_2.py` проверяет входной JSON v0.2 без
Excel-генерации и без открытия Excel-шаблонов.

Покрытые области:

- верхний уровень JSON;
- `output_mode`;
- `project_blocks`;
- `source_pages`;
- `subsections`;
- `items`;
- связку `price_kzt` / `price_confirmed_by_igor`;
- `safety_flags`;
- `metadata`.

Validator возвращает структурированный результат:

- `is_valid: bool`;
- `errors: list[str]`;
- `warnings: list[str]`.

Пустой список `items` внутри subsection допускается для демонстрационного или
чернового JSON, но validator выдаёт warning. Отсутствие поля `items` является
ошибкой.

## 4. Что категорически нельзя ломать

В следующей кодовой фазе нельзя ломать:

- текущий MVP-заполнитель;
- существующие тесты;
- CI;
- Excel-шаблон;
- формулы;
- подписи;
- шапку и реквизиты;
- логотип, drawings и media parts;
- правило: Excel-файлы не добавлять в Git;
- правило: финальные цены и сроки не утверждать автоматически.

Любая Excel-генерация должна сохранять output только вне Git-проекта и не
перезаписывать существующий output-файл.

## 5. Открытый выбор перед кодом

Перед началом Excel-генерации нужно выбрать первый режим реализации:

- `separate_workbooks_by_block`;
- `single_workbook_sections`.

Режим `both` лучше не реализовывать первым. Его безопаснее собирать после того,
как один из базовых режимов уже стабилен.

## 6. Сравнение режимов генерации

### separate_workbooks_by_block

Плюсы:

- технически безопаснее;
- меньше строк в одном workbook;
- проще переиспользовать текущий MVP-подход;
- меньше риск сломать формулы;
- меньше риск сломать подписи;
- меньше риск сломать логотип, drawings и media parts.

Минусы:

- не повторяет структуру реального КП №268;
- в реальном КП №268 оба пятна были в одном листе;
- для клиента или менеджера может быть неудобно иметь несколько файлов вместо
  одного общего КП.

### single_workbook_sections

Плюсы:

- лучше соответствует реальному КП №268;
- формирует один общий КП;
- позволяет вывести секции `Пятно 8` и `Пятно 9` в одном документе;
- лучше подходит для целевого бизнес-сценария общего КП.

Минусы:

- технически рискованнее;
- нужно работать с большим количеством строк;
- нужно аккуратно размещать секции и subsections;
- нужен общий итог;
- может понадобиться расширенный шаблон;
- выше риск повредить формулы, подписи, шапку, логотип или drawings.

## 7. Предварительная рекомендация

Для первого кодового шага рекомендуется `separate_workbooks_by_block` как более
безопасный технический старт.

Этот режим позволяет проверить v0.2 JSON, validator, output naming и базовую
генерацию без немедленного риска динамической вставки строк и сложной общей
таблицы.

При этом целевой бизнес-сценарий обязательно должен поддерживать
`single_workbook_sections`, потому что реальный КП №268 был общим: `Пятно 8` и
`Пятно 9` находились в одном листе.

## 8. Что должен сделать следующий кодовый этап

Следующий кодовый этап должен:

- не трогать OCR;
- не делать reconciliation;
- не делать динамическую вставку строк;
- взять уже валидный JSON v0.2;
- сначала реализовать выбранный `output_mode`;
- сохранять output только вне Git-проекта;
- не перезаписывать существующий output;
- не добавлять Excel-файлы в Git;
- сохранять статус черновика;
- не утверждать финальные цены и сроки.

Если выбран `separate_workbooks_by_block`, реализация должна формировать
отдельный output на каждый блок из `project_blocks[]`.

Если выбран `single_workbook_sections`, сначала нужен отдельный анализ шаблона
и безопасного количества строк. Без этого нельзя переходить к динамическому
расширению таблицы.

## 9. Что не входит в следующий кодовый этап

В следующий кодовый этап не входят:

- OCR;
- чтение проектного PDF;
- сверка КП с проектом;
- финальные цены;
- финальные сроки;
- автоматическое подтверждение `project_spec.json`;
- динамическая вставка строк в Excel;
- режим `both`, если Игорь отдельно не выберет его как цель этапа.

## 10. Риски перед началом кода

Основные риски:

- больше 5 позиций на блок;
- необходимость расширенного шаблона;
- риск сломать формулы;
- риск сломать подписи;
- риск сломать логотип, drawings или media parts;
- риск принять черновой JSON как подтверждённый проект;
- риск смешать source reference и название секции КП;
- риск записать output внутрь Git-проекта;
- риск случайно добавить Excel-файл в Git;
- риск восприятия черновика как финального КП.

## 11. Следующее решение Игоря

Перед кодом Игорю нужно выбрать первый режим реализации:

```text
A) separate_workbooks_by_block
B) single_workbook_sections
```

Предварительная техническая рекомендация: начать с
`separate_workbooks_by_block`, затем отдельно перейти к
`single_workbook_sections` как к целевому бизнес-сценарию.
